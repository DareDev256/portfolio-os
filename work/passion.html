Why I built it

I wanted to know what an autonomous AI agent looks like when you take it seriously as software — versioned, observable, restart-safe, cost-traced, with durable state across crashes and a memory layer that survives sessions. Most agent demos are a single jupyter notebook. Production agents are a system. Passion is the system I built to find out what that means.

It runs 24/7 on a Mac Mini (always-on agent ops) and syncs with a MacBook Pro (interactive control) over Tailscale + Syncthing. It autonomously discovers, scores, tailors, and applies for AI engineering roles on my behalf — but the job pipeline is the use case, not the point. The point is the architecture.

The three pieces

Passion Agent — the engine

  • Goal-driven KPI engine — every loop iteration asks "what KPI moves most for the lowest cost?" and picks the next action accordingly.
  • Adaptive scheduling — backs off when API quota or rate limits tighten; bursts when costs and limits permit.
  • Durable execution checkpoints — every long-running task writes intermediate state to SQLite. On crash/restart, the agent resumes from the last checkpoint, not from scratch.
  • Per-call cost tracing — every model call is logged with input/output tokens, cached-vs-uncached split, and rolled up to per-task and per-day budgets.
  • 6-stage career pipeline — discover → score → tailor → apply → track → learn. Each stage is a separate module with its own retry/idempotency contract.

PACT Dashboard — the control room

  • Real-time command terminal — Web Terminal (PTY shell) inside the browser, with full access to the agent's host machine.
  • 121 React components across 10 tabs — task list, cost ledger, memory browser, KPI charts, error timeline, deployment console.
  • 76 API routes + 81 React Query hooks — every dashboard view is a query against a backend route, cached + invalidated cleanly.
  • Web Push notifications — agent surfaces decisions that need human approval through VAPID push, not email.
  • STT voice input — Web Speech API for command-by-voice when I'm not at the keyboard.

Passion Memory MCP — the persistent brain

  • Knowledge graph — entities, relationships, edges built from observed interactions and explicit save commands.
  • Vector embeddings for semantic recall across hundreds of stored memories.
  • Somatic markers (Damasio) and narrative identity (Bruner) — research-derived structures for tagging memories with emotional valence and biographical coherence.
  • Cross-session handoff — every Claude Code session loads the relevant slice of memory at start and saves a checkpoint at end. No cold starts.
  • Exposed as an MCP server — any Claude-compatible surface can call memory_store, memory_recall, session_save, etc. as tools.

Patterns I'd carry to a job tomorrow

  • Durable checkpoints > idempotency in long-running agent tasks. Idempotency is "safe to retry"; checkpoints are "resume from where you crashed." Both matter, but checkpoints are what makes a 6-hour task survivable.
  • Cost tracing has to be per-call, not per-day. If a single ill-formed prompt blows your day's budget at 4am, you need to know which prompt and which input — not just the line item on the bill.
  • Memory is multi-typed. Treating every "fact" as the same kind of memory makes everything worse. User profile facts, project state, feedback corrections, and external references all have different retrieval and update patterns.
  • The control room matters as much as the engine. An agent without a dashboard is a black box you stop trusting. The dashboard is the thing that makes the agent feel operable, not just running.
  • MCP is a real production pattern. Wrapping the agent's tools as an MCP server makes them reusable across surfaces — Claude Desktop, Claude Code, custom clients — and forces clean tool schema design.

Honest tradeoffs

  • Passion is solo-built. It works well for one operator (me) and has not been hardened for multi-tenant use. If I were rebuilding for a team, I'd start with the same agent loop pattern but invest much earlier in role-based access, audit logging, and per-user budget caps.
  • The dashboard is feature-rich because it's my daily driver. A v1 production dashboard would be 20% of these features.
  • The memory layer is opinionated — somatic markers and narrative identity are pulled from cognitive science, not from a standard agent framework. That's intentional but means it's not drop-in compatible with LangGraph / CrewAI / etc.
