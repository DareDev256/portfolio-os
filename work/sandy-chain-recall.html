Sandy Chain-Recall

Recognition, without asking. The silent institutional memory of a luxury hotel chain — when a member walks into any property, even one they've never visited, front-of-house staff is briefed on who they are, what they prefer, and how to treat them. The AI is invisible to the guest.

The pitch

Your luxury hotel chain already pays for Oracle OPERA. Your front desk already enters every preference, allergy, complaint, amenity request. You are simply not using that data at the moment of arrival. Sandy Chain-Recall is the AI layer that unlocks the data you already own.

We demo it deployed against the chain we'd target first: Rosewood Hotels & Resorts — 38 properties, 23 countries, all OPERA-backed via Hapi. Three real properties anchor the demo: Rosewood Hong Kong, Rosewood Sand Hill, Rosewood London.

Architecture

QR scan  →  POST /api/arrive
                    │
                    ├──→ publish "computing" event (eventBus)
                    │
                    ├──→ compose(): Claude reads guest profile
                    │    via tool use (get_guest_history),
                    │    writes 12-section structured brief
                    │
                    └──→ publish "brief" event
                                 │
                  GET /api/stream (SSE) ───→ /staff tablet
                                                  │
                                                  ├──→ render brief + chime
                                                  └──→ Whisper button →
                                                       /api/whisper →
                                                       ElevenLabs Turbo
                                                       (Sandy + Hill voices)

The composer is a tool-use agent, not a template

The composer is Claude Opus 4.7 with a single tool: get_guest_history(guestId). The system prompt enforces a 12-section brief schema (arrival intel · accessibility · prep actions · amenity replenishment · suggested questions · local suggestions · discretion flags · emotional context · etc.). The model calls the tool, reads the cross-property history, and writes structured prose under each section. Compared to a templated assembly pipeline, the tool-use approach produces briefs that weigh conflicting preferences and surface non-obvious connections (e.g., the guest is a HK regular but had one bad London stay — that context matters at Sand Hill).

The Oracle OPERA boundary is a real production seam

lib/sources/opera.ts is the integration boundary. Today it points at a seed corpus of fictional guests for the demo. In production, it's the OHIP REST client. The composer doesn't know which is which — that's the whole point.

SSE for live tablet wake

When the guest scans the QR (or, in production, hits a BLE beacon or valet license-plate camera), an event publishes on an in-memory pub/sub bus, and an SSE connection pushes the computing → brief state transitions to the staff tablet. Loading skeleton + audio chime sells the magic. In production: Redis pub/sub.

ElevenLabs earpiece, not guest-facing TTS

The AI is invisible to the guest. The voice layer is staff-side: a butler-timbre audio brief whispers to the bell captain's headset as the guest approaches. Never voice TO the guest. Custom-cloned Sandy + Hill duo voices via ElevenLabs Turbo + Multilingual v2 — 5-language guest-greeting samples for the staff to use.

Wifi parachute

Every demo guest × property combo has a hand-tuned cached brief. If the Claude API errors or takes > 6s, we fall back to the cached brief silently. The demo never breaks. In production: graceful degradation with audit logging.

Privacy & compliance scaffolding

  • GDPR Art. 17 / CCPA §1798.105 cited verbatim in the privacy opt-out flow — the demo shows a guest exercising their right to be forgotten.
  • Per-property opt-out plumbed end-to-end.
  • Every memory carries a ledger: which property created it, which staff member, which interaction. Auditable on guest request.
  • Data residency designed-in (EU stays don't leave EU); SOC 2 Type II target by production month 6.

What I'd build next (production v1, ~4–6 weeks)

  • Presence detection beyond QR — BLE beacons at property entry, license-plate recognition at valet, member-app geofence + opt-in foreground notification, staff walk-in fallback.
  • Memory layer — Postgres + pgvector against Hapi's OPERA event stream. Decay + conflict resolution (90-day relevance half-life; contradicting facts surface for human review). Source-grounded composition.
  • MCP server wrapper — composer becomes an MCP server so Claude Desktop, the Rosewood app, or any Claude-powered surface can call get_guest_history and compose_brief as tools. Per-property + per-staff-role tool surface scoping.
  • Staff role permissions — concierge sees the full brief, housekeeping sees only room-prep details, F&B sees only dietary + drink preferences. Audit log on every read.
  • Quality loop — staff one-tap feedback after each interaction ("useful / partial / wrong"); wrong-flagged briefs retrain retrieval ranking; weekly GM digest.
