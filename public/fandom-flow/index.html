Anyone who can edit the wiki can stop this agent. It reads User:RawBOT/shutoff before it reads anything else. If the first line of that page is not exactly RUN, the run aborts without touching the wiki. Go and try it.

how to halt it

Edit one page

Change the first line of the shutoff page to anything other than RUN. The next run reads it, aborts, and reports the halt on Discord. No permissions and no coordination with me required.

why

The block log

On Wikipedia the bots blocked for "no emergency button" and "not responding to the run page" were the ones whose switch did not work. A switch nobody can reach is not a switch.

rate

One edit per day

One edit per UTC day, never flagged bot so every change stays visible in Recent Changes. Operator: James Dare, reachable on the account's talk page.

The scheduled job is an applier, never an author. It cannot invent an edit. It drains a queue written and reviewed in advance, and if that queue is empty it writes a dated line in its own userspace rather than improvising in article space.

01 - session

Research & queue

Edits are researched against patch notes and the game, then written to queue.jsonl with the exact operation, expected match count, and a citation.

02 - 09:00 daily

Verify premise

A queue entry is a hypothesis. Before firing, the job re-reads the live page and confirms the premise still holds. Drifted page, blocked entry.

03 - apply

One edit

One edit per UTC day, never flagged bot. If a human already edited that day, the job exits without touching anything.

04 - independent

Verify result

A separate reader queries the wiki and counts distinct edit-days. It reads no state file, no log, no queue - only what the wiki says happened.

Seven refusals stand between the queue and article space. Each one blocks the entry and moves on rather than guessing.

  • No authoring. The job applies queue entries. It has no path to write an edit nobody reviewed.
  • Exact match counts. Every replacement declares how many matches it expects. Off by one and the entry blocks instead of mangling the page.
  • Blanking guard. A result under 90% of the original length is refused unless the entry explicitly declares a shrink.
  • No-op refusal. MediaWiki silently discards an identical revision - which would break the streak while reporting success. Identical output is treated as failure.
  • Namespace lock. MediaWiki:, Template: and Module: are refused whatever the queue says.
  • Redirects always survive. The move operation cannot suppress the redirect, so no inbound link ever breaks.
  • Human deference. If the account already edited that UTC day, the job does nothing.

Every number on this page is fetched at build time from the public MediaWiki API of both wikis, then rendered. Nothing is hardcoded, so a figure that looks wrong is a bug in the fetch rather than a claim in the copy.

fetch

fetch_data.py

Queries siteinfo, users, usercontribs, recentchanges and logevents on both wikis, and inlines each wiki's own site icon as a data URI.

render

build_page.py

Renders this page from data.json. Emits pure ASCII with numeric character references, since the page cannot declare its own charset.

verify

streak_verify.py

Reads the live wiki and counts distinct UTC edit-days. Reads no state file, no log and no queue - the job's claim is not the measurement.
